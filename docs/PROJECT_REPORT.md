## Abstract

This report presents the design, technical architecture, and implementation of an **Intelligent Invoice Processing and Semantic Search Engine** developed during my internship at Ernst & Young (EY). In modern enterprise financial workflows, manual invoice entry and non-standardized document formats create severe operational bottlenecks, including high error rates, processing delays, and poor search accessibility. Traditional template-based OCR tools fail when document layouts vary, while standard SQL databases cannot perform contextual natural language searches over unstructured documents.

To solve these challenges, the project delivers a cloud-native microservice solution built with **React 18** and **Vite** for the frontend, **Python 3.11** and **FastAPI** for the backend engine, **PostgreSQL** for relational metadata storage, **Qdrant Vector DB** for dense vector similarity search, and **Azurite** for local Azure Blob Storage emulation. Raw PDF streams are archived securely upon upload, key financial attributes (vendor name, invoice number, date, amounts, tax, and line items) are extracted using **Azure AI Document Intelligence** (`prebuilt-invoice`) with local fallback parsers (**PyPDF / Tesseract OCR**), and raw document text is encoded into 384-dimensional dense vectors using **SentenceTransformers (`all-MiniLM-L6-v2`)**.

The application features a modern dark-theme **Glassmorphic Dashboard** equipped with real-time service health monitors, dropzone ingestion, filter chips, and side-by-side invoice previews. The entire multi-container architecture is orchestrated using **Docker Compose**, delivering sub-second natural language query performance, zero data loss, and seamless operational reliability.

## 1. Introduction, Problem Statement and Objectives

### 1.1 Background & Context
Enterprise accounting departments and shared service centers process thousands of invoices daily from diverse suppliers and vendors. These documents arrive in non-standardized formats—ranging from native digital PDFs generated by ERP tools to scanned paper receipts and images. Manually reading, verifying, and transcribing invoice details into accounting systems is labor-intensive, taking between 5 to 10 minutes per document with an average human data entry error rate of 3–5%.

![Figure 1: Sample Unstructured Vendor PDF Invoice Document](file:///e:/EY_intern/docs/images/fig1_sample_invoice_pdf.png)  
*Figure 1: Sample unstructured vendor PDF invoice document containing layout fields, vendor details, and line-item tables prior to processing.*

### 1.2 Problem Statement
Traditional invoice processing relying on legacy optical character recognition (OCR) uses rigid coordinate templates. When a vendor updates their invoice layout, template-based extraction fails completely. Furthermore, once invoices are stored, corporate databases only support exact keyword or field matching. Finance teams are unable to execute contextual semantic queries such as *"find all logistics receipts for office supplies exceeding $5,000 from last quarter"* without pre-tagged categories or manual audit searches.

### 1.3 Objectives
- **Build a Full-Stack GenAI Engine**: Develop an end-to-end web system using React 18 and Python/FastAPI.
- **Automated Blob Ingestion**: Archive raw PDF streams securely in Azurite (Azure Blob Storage emulator) for file auditability.
- **Multimodal Document AI Extraction**: Extract structured key-value pairs (Vendor Name, Invoice ID, Date, Amount, Tax, Line Items) using Azure AI Document Intelligence with PyPDF fallback.
- **Dense Vector Embedding & Semantic Search**: Encode text into 384-dimensional dense vector embeddings using SentenceTransformers (`all-MiniLM-L6-v2`) and index them in Qdrant Vector DB.
- **Hybrid Query Execution**: Support dual-mode retrieval combining structured SQL filtering with natural language vector similarity search.
- **Glassmorphic React Dashboard**: Provide a responsive dark-mode dashboard featuring live service status monitoring, drag-and-drop ingestion, and invoice table preview.
- **Containerized Orchestration**: Run the complete multi-service stack seamlessly via Docker Compose.

## 7. Database & Vector Schema Design

### 7.1 Data Storage Strategy
The system uses a dual-database model: PostgreSQL stores structured relational fields, while Qdrant handles high-dimensional vector embeddings.

| Entity / Store | Storage System | Purpose & Contents |
|---|---|---|
| **Raw PDF Blobs** | Azurite (Azure Storage) | Binary stream of uploaded invoice files (`invoices-raw`) |
| **Structured Metadata** | PostgreSQL (`invoices`) | Vendor name, invoice ID, date, total amount, tax, currency, status, line items JSON |
| **Semantic Vectors** | Qdrant (`invoices_vector_index`)| 384-d dense vector embeddings, metadata payloads, similarity scores |

### 7.2 Relational Schema (`invoices` Table)
```sql
CREATE TABLE invoices (
    id SERIAL PRIMARY KEY,
    filename VARCHAR(255) NOT NULL,
    blob_url VARCHAR(512),
    vendor_name VARCHAR(255),
    invoice_number VARCHAR(100),
    invoice_date DATE,
    total_amount DOUBLE PRECISION,
    tax_amount DOUBLE PRECISION,
    currency VARCHAR(10) DEFAULT 'USD',
    status VARCHAR(50) DEFAULT 'PENDING',
    raw_text TEXT,
    line_items_json JSONB,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

![Figure 7: PostgreSQL Database Table View & Stored Invoice Metadata](file:///e:/EY_intern/docs/images/fig7_postgresql_records.png)  
*Figure 7: PostgreSQL database table view displaying structured invoice metadata records, status tracking (COMPLETED/PROCESSING), and JSONB line items.*

### 7.3 Qdrant Vector Collection Schema
- **Collection Name**: `invoices_vector_index`
- **Vector Dimension**: 384 dimensions (matching `all-MiniLM-L6-v2`)
- **Distance Metric**: Cosine Similarity (`Distance.COSINE`)

## 14. Engineering Decisions and Challenges

- **Choosing Hybrid Storage**: Combining PostgreSQL for transactional integrity with Qdrant for vector search provided the optimal balance of data consistency and contextual search flexibility.
- **Azurite Storage Emulation**: Integrating local Azurite cloud emulation eliminated cloud cost dependencies during development while ensuring 100% Azure production compatibility.
- **Failover Extraction**: Designing a local PyPDF/Tesseract fallback ensured system stability during network outages or API quota limits.
